# Migration set: lawrider.uk — British law and UK court decisions, nothing else.
#
# 134 of the 220 migrations. What is here: the service schema the backend boots on
# (users, api_keys, billing, cost tracking, documents, oauth, consultations) and
# uk_* — the register, provision text, point-in-time intervals, amendments,
# judgments and the Find Case Law access gate. 14 uk_ tables out of 129 total.
#
# ── Why this file exists ──────────────────────────────────────────────────
# The full history cannot build a database from zero. 126_spain_legal_data.sql
# opens with "Tables already exist from prior schema" and then ALTERs tables
# nothing ever created, so a fresh run stops there with `relation
# "spain_eurlex_legislation" does not exist`. Every box so far was therefore born
# from a dump of another box, not from its own migrations. Verified 2026-09-19.
#
# ── How the list was chosen ───────────────────────────────────────────────
# Not by filename. Each migration was applied alone to an empty database and
# pg_tables diffed before and after, which is the only way to see that
# 129_offshore_jurisdictions_data.sql carries Swiss registers, that
# 102_ip_and_securities_tables.sql carries Ukrainian patents, or that
# 137_es_boe_sumarios.sql creates four Spanish tables. Removed on that evidence:
# Ukrainian legislation and its editions, the court-registry scraper, the bar
# register, IP and securities, EU law, ICIJ offshore, Spain, and the Baltic,
# Nordic and Western European court corpora — 54 tables in all.
#
# ⚠ Automation found the candidates; the calls below were made by hand:
#   037_add_time_billing.sql        KEPT. Flagged only because its table is
#                                   `active_timers`, which a prefix rule read as
#                                   the Ukrainian `act`. It is billing.
#   155_uk_ie_court_decisions.sql   KEPT. It also creates ie_court_decisions, but
#                                   it is what creates uk_court_decisions. The
#                                   Irish table stays empty.
#   100_legislation_monitoring.sql  DROPPED, reluctantly: it needs the Ukrainian
#                                   `legislation` table, and takes
#                                   user_notifications with it. Nothing in
#                                   mcp_backend/src reads that table.
#   195_uk_legislation.sql          KEPT — and an earlier automated pass dropped
#                                   it, "converging" by discarding the core UK
#                                   migration. It was failing on a missing
#                                   pg_trgm, which is now 000_extensions.sql.
#
# Verified: all 134 apply clean to an empty database, and the backend boots
# against the result — /health/ready 200, five uk_* tools advertised, the
# point-in-time query planning on its index.
#
# Listed by name, not by glob: adding a migration to a deployment should be a
# decision someone makes, not something a pattern does on their behalf. A name
# here that matches no file fails the run loudly.
